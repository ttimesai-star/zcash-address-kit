# Contributing to zcash-address-kit

Thanks for helping. This is a small validation library, so the rules are short. They follow the spirit of the
[librustzcash contributing guide](https://github.com/zcash/librustzcash/blob/main/CONTRIBUTING.md) (clean
history, every behaviour change documented and tested), adapted to a TypeScript package.

## Code of Conduct

Participation is governed by the
[Zcash Code of Conduct](https://github.com/zcash/zcash/blob/master/code_of_conduct.md).

## Questions and bug reports

- Search existing issues first.
- For a wrongly accepted or wrongly rejected address, include the address string (testnet or a published test
  vector if possible, never an address you need to keep private), the options you passed, the result you got,
  and what librustzcash (`zcash_address`) or the ZIP says it should be.
- Security-relevant problems (for example a malformed address that is accepted): please open a GitHub security
  advisory on this repository instead of a public issue.

## What a change must include

1. **A test for every behaviour change.** Prefer vectors produced by reference code:
   official files from [zcash/zcash-test-vectors](https://github.com/zcash/zcash-test-vectors) (copied
   unmodified into `test/vectors/official/`, with the source commit in `test/vectors/README.md`), or new entries
   generated by `scripts/gen_reference_vectors.py`. Hand-written strings are acceptable for encoding edge cases.
2. **A reference for every validation rule.** Cite the ZIP section, or the librustzcash function, in the code
   comment or the pull request. Where the ZIP text and librustzcash disagree, say so explicitly (see
   "Reference behaviour" in the README) and add an option rather than silently picking one.
3. **Documentation.** If the public API, an error code or the accepted address set changes, update `README.md`
   (and `src/errors.ts` for error codes) in the same commit.
4. **Green checks.** `npm test` (build + full suite, including the 4 194 368-byte F4Jumble vector) must pass locally and in
   CI (Node 22 and 24). `npm audit --omit=dev` must report no vulnerabilities.

## Git usage

- Branch from `main`; open the pull request against `main`. Opening it as a Draft until CI is green is welcome.
- Commits should be discrete semantic changes. No "work in progress" or "fix typo" commits in the final
  history; fold review fixes into the commit they belong to (`git rebase --autosquash` or `git revise`).
- Commit messages: a short imperative summary line (≤ 72 characters), a blank line, then what changed and why.
- Pull requests are merged with merge commits so that history is preserved.

## Coding style

- TypeScript, ES modules, `strict` compiler settings (see `tsconfig.json`). No native code, no WASM.
- No new runtime dependencies without discussion. The only runtime dependency is `@noble/hashes` (audited).
- Validation only: the library must never handle keys, seeds or network access.
- Public functions and options get a TSDoc comment.
- Inputs are untrusted: keep length caps and avoid work that grows faster than linearly with input size.

## Releases

Semantic versioning. Releases are published to npm from CI with provenance once the package reaches 1.0.

## Use of AI assistants

Most of the existing code was written with an AI coding assistant (Claude) under the maintainer's direction.
Contributions written with AI assistance are accepted on the same terms as any other: you are responsible for
the change, it must come with tests from reference vectors, and you must be able to answer review questions
about it. Please say in the pull request if an assistant wrote substantial parts of it.
